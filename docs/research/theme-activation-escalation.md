# External theme activation escalation on macOS

Research cutoff: 2026-09-02

## Scope and evidence standard

This note asks a narrow question: after a theme is installed, can a separate macOS app activate it without simulating the target app's UI or writing private preferences?

Only first-party documentation, public scripting dictionaries, documented CLIs and plugin APIs, and official source repositories count as evidence. A documented theme installation directory does not by itself prove that changing the active theme is supported. Likewise, a setting name does not prove that an already-running app watches external edits.

Status terms:

- `automatic`: every switch can use a verified supported command, API, scripting interface, or reload mechanism.
- `automatic after setup`: one-time consent, companion code, profile choice, or target configuration is required. Later switches need no action in the target app.
- `manual every switch`: installation can be automated, but each activation still needs a documented in-app selection.
- `unsupported`: the checked first-party interfaces omit theme activation and the remaining known routes violate this note's constraints.
- `unresolved`: the gathered evidence does not justify either an automatic or unsupported claim.

A sandboxed macOS switcher may also need one-time user authorization for each configuration folder. That file-access concern is separate from whether the target app supports activation.

## Automatic paths worth implementing first

1. **btop** has the cleanest direct route. Change one documented key and signal each process with the reload signal handled in official source.
2. **iTerm2** has the richest target-owned API. It can apply an installed color preset to shared profiles or individual live sessions without private preference writes.
3. **Terminal.app** is scriptable at the exact per-tab profile boundary. The cost is one-time Automation consent and explicit iteration over existing tabs.
4. **Sublime Text** becomes reliable after a small companion package. The documented CLI starts the command; the public plugin API owns the settings change.
5. **Zed** is automatic only for a preconfigured light/dark pair driven by global macOS appearance. It is useful, but too restrictive and intrusive to present as arbitrary theme activation.

## Gaps that remain unresolved

- Whether an external atomic edit to Zed's `settings.json` is watched and applied to all open windows, including behavior while a settings profile is active.
- Whether Zed exposes any supported deep link, CLI action runner, or extension API that can select a named theme.
- Whether JetBrains marks a theme-changing API as public and stable for third-party plugins, and whether an external process can invoke that plugin without inventing its own unauthenticated IPC service.
- Whether the current Obsidian CLI has a supported theme command, and whether Obsidian's public plugin API has both a supported theme setter and a supported external invocation channel.
- Whether Warp reapplies the currently selected custom theme when its YAML file changes. The docs only guarantee that directory changes are reflected in theme discovery.

Until those points have first-party evidence, the adapter should report `installed, activation requires app action` rather than silently editing preferences or claiming success.

## Excluded routes

Do not use:

- Accessibility-driven clicks or keystrokes.
- `defaults write` against undocumented application keys.
- Direct writes to JetBrains settings XML, Xcode preferences, Terminal preferences, Warp state, or Obsidian's undocumented appearance state.
- Process restarts presented as a reload API when the app does not document restart as its activation mechanism.
- A companion plugin that opens an unauthenticated local port without a target-documented security and lifecycle model.
